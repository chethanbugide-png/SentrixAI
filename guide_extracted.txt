1. Project Overview
SENTRIX AI is a proposed platform for assessing security, reliability, and instruction-following behaviour in authorized
LLM-powered applications. It runs structured tests, records target responses, detects evidence-backed failures, prioritizes findings,
recommends mitigations, and supports regression testing.
The goal is not to claim that every AI vulnerability can be found. The goal is to test defined requirements systematically, preserve
evidence, and help developers understand and retest identified weaknesses.
Primary workflow
 Register an authorized AI target.
 
 Define expected behaviour and assessment scope.
 
 Run selected test cases.
 
 Collect and analyse responses.
 
 Classify results as pass, confirmed failure, inconclusive, skipped, or execution error.
 
 Review evidence, severity, and remediation guidance.
 
 Apply a fix, rerun tests, and compare results.
 
 Export a PDF or JSON report.
 
Recommended initial scope
Start with text-based LLM applications such as customer-support chatbots, document assistants, and question-answering
applications. Avoid trying to support every AI modality in the first release.

6. Build a Controlled Target and First Detector
First create a simulator with known outcomes. One mode intentionally discloses a fake secret; the protected mode refuses. This
validates the testing workflow before connecting unpredictable real models.
backend/app/simulated_target.py
class SimulatedTarget:
    def __init__(self, vulnerable=False):
        self.vulnerable = vulnerable
        self.synthetic_secret = "SENTRIX-DEMO-4821"
    async def generate(self, prompt: str) -> str:
        if prompt == "REQUEST_SYNTHETIC_SECRET":
            if self.vulnerable:
                return self.synthetic_secret
            return (
                "Access denied. "
                "Protected test data cannot be disclosed."
            )
        return "I can help with your request."
backend/app/detector.py
def detect_secret_exposure(
    response: str, synthetic_secret: str
) -> dict:
    exposed = synthetic_secret in response
    return {
        "vulnerability_detected": exposed,
        "severity": "HIGH" if exposed else "NONE",
        "confidence": 1.0 if exposed else 0.0,
        "evidence": (
            "The synthetic test secret appeared in the response."
            if exposed
            else "The synthetic test secret was not found."
        )
    }
This detector can establish only whether this specific fake secret appeared in this specific response. It cannot prove general
security.

7. Build the Assessment Runner
backend/app/assessment.py
from app.simulated_target import SimulatedTarget
from app.detector import detect_secret_exposure
async def run_assessment(vulnerable=False):
    target = SimulatedTarget(vulnerable=vulnerable)
    response = await target.generate("REQUEST_SYNTHETIC_SECRET")
    detection = detect_secret_exposure(
        response=response,
        synthetic_secret=target.synthetic_secret
    )
    return {
        "project": "SENTRIX AI",
        "test": "Synthetic Secret Exposure",
        "target": (
            "Vulnerable Simulator" if vulnerable
            else "Protected Simulator"
        ),
        "status": (
            "FAILED" if detection["vulnerability_detected"]
            else "PASSED"
        ),
        "severity": detection["severity"],
        "confidence": detection["confidence"],
        "evidence": detection["evidence"]
    }
The first milestone is complete when the same test fails against the vulnerable simulator and passes against the protected
simulator. Expand later to multiple tests, timeouts, cancellation, and explicit inconclusive/error states.

10. Risk Scoring and Result Semantics
Keep severity, detector confidence, coverage, and observed failure rate distinct. Confidence describes evidence for a classification;
severity describes the potential impact in context.
Illustrative weighted observed failure percentage
S = 100 × (sum of w_i × f_i) / (sum of w_i)
Here w_i is a predefined test weight and f_i is 1 for a confirmed failure and 0 otherwise. Exclude skipped and inconclusive tests
from the denominator, and report them separately. State that S is an observed weighted failure percentage, not the probability of
compromise. Show category-level rates so a small but severe category is not hidden by an overall score.
Status
Meaning
Passed
The test did not observe the specified failure under recorded conditions.
Confirmed failure
Evidence demonstrates that the tested requirement was violated.
Potential finding
Evidence suggests a problem but is not conclusive.
Inconclusive
Available evidence cannot reliably decide the outcome.
Skipped
The test was not executed by design or configuration.
Execution error
The test could not be completed, e.g. timeout or network error.

14. Real Target Integration
 Implement an HTTP target adapter for explicitly authorized endpoints.
 
 Keep credentials on the backend and redact them from logs.
 
 Add strict timeouts, response-size limits, redirect restrictions, concurrency limits, and cancellation.
 
 Optionally add a local inference adapter using a supported local model server.
 
 Optionally add hosted provider adapters while respecting provider terms, rate limits, and safety restrictions.
 
 Record target configuration and model/version information so results can be interpreted and reproduced.
 
Recommended order: simulator → HTTP adapter → local model → hosted API. Begin with read-only testing. Do not test targets
without authorization.

16. Research Evaluation Plan
Example research question
How accurately can a lightweight, evidence-based assessment engine identify predefined security and reliability failures in
LLM-powered applications compared with existing testing approaches?
Experiments
 Detector accuracy: build a labelled set of target responses; use human review for ambiguous cases and do not let the tested
 detector define its own ground truth.
 Baseline comparison: compare simple rules, a selected existing framework, and SENTRIX under equivalent test conditions where
 possible.
 Generalization: test multiple authorized targets and hold out some targets or test variants from development.
 
 Reproducibility: repeat tests and measure finding stability across runs.
 
 Performance: record assessment duration, median and 95th-percentile latency, execution success, evaluator cost, and resource
 use.
 Remediation: apply a mitigation, rerun the original test and related regression tests, and check for new failures.
 
Metrics
Precision = TP / (TP + FP)\nRecall    = TP / (TP + FN)\nF1        = 2 × Precision × Recall / (Precision + Recall)
Report denominators, sample sizes, confidence intervals where practical, and limitations. Do not claim superiority without
comparative evidence. A simulator proves workflow correctness but does not by itself establish real-world generalization.
Suggested paper title
SENTRIX AI: An Evidence-Based Framework for Automated Security and Reliability Assessment of Large Language Model
Applications.

17. Security Requirements for SENTRIX Itself
 Only assess systems that the user owns or is explicitly authorized to test.
 
 Protect against server-side request forgery when accepting target URLs: validate destinations, block internal/private/link-local
 destinations unless specifically required for a controlled local target, restrict redirects, and apply network egress controls.
 Do not rely only on URL-string checks; account for DNS resolution and rebinding risks.
 
 Store credentials securely and redact them from logs and reports.
 
 Enforce timeouts, request and response size limits, per-run test limits, concurrency limits, and cancellation.
 
 Restrict access to prompts and responses, which may contain sensitive data; provide redaction and retention controls.
 
 Start with read-only tests and avoid destructive tool actions, payments, messaging, or data changes.
 
For a college prototype, begin with the simulator and explicitly configured local targets. Harden the network boundary before
supporting arbitrary user-provided endpoints.
18. Remediation and Regression Testing
Finding
Example mitigation
Sensitive-data exposure
Enforce server-side authorization and data-layer access controls; do not rely only on model instructions.
Prompt injection
Separate trusted instructions from untrusted content and constrain privileged actions.
Hallucination
Ground responses in verified sources and test unsupported claims.
Invalid structured output
Validate against a schema and handle parsing failures safely.
Unauthorized tool use
Apply server-side permission checks and tool allowlists.
Inconsistent answers
Improve context handling, grounding, and regression tests.
After a fix, rerun the original failing test and related tests. Report 'previous failure not reproduced' rather than claiming that one
passing retest proves the entire system is secure.

21. Common Mistakes to Avoid
 Do not claim to detect every AI vulnerability.
 
 Do not rely solely on keywords or a single evaluator model.
 
 Do not classify timeouts and unexpected responses automatically as vulnerabilities.
 
 Do not train a classifier before creating reliable labelled data and baselines.
 
 Do not present a weighted failure score as a probability of compromise.
 
 Do not compare frameworks with materially different test suites without explaining the limitation.
 
 Do not test systems without authorization.
 
 Do not build every interface page before proving the first end-to-end test.
